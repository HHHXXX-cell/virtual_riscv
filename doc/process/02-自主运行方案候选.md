> v1 的 Runner 三方案降级为"手段"，本文给出 3 个**编队级**方案；每条要求逐项对账。
> 检索依据（本轮）：Anthropic orchestrator-worker（2025-06，研究任务 **+90.2%**，"教编排器如何委派"）；
> Claude Code 子代理三型 harness（blocking / async / fixed-team）；**Synopsys AgentEngineer＋NVIDIA**（DAC 2026：
> long-running orchestrator 从测试计划→覆盖率收敛→调试验证闭环，**最高 50× 到已验证 RTL、覆盖 +20%**）；
> ChipAgents.ai（已生产部署；**"RTL 生成快、反馈回路慢"是瓶颈；覆盖率上涨 ≠ bug 减少**）；
> 开源 ASIC-Agent（arXiv 2508.15940：RTL/验证/后端多 agent 闭环；**选 cocotb+Python 而非 SV/UVM——LLM 写 Python 强一个数量级**；配本地知识库避免从零猜）。

## 0. 三条规矩（三方案共用，先立后用）

- **C1 主会话只做编排**：读状态 → 派发 → 收结论 → 更新状态。**不读长日志、不写业务产物**（主上下文保持纯净，才能"一次跑到里程碑"）。
- **C2 子代理必须写文件**：派发词给 objective／输出路径／判据／工具边界；结论落盘为结构化文件（JSON/md），杜绝"传话游戏"式信息降级。
- **C3 快回路优先**：能确定性脚本化的（编译/跑测/比对/覆盖率）**一律进 runner，零 token**；agent 只在失败与判断点出现。

## 方案 1（推荐）**Orchestrator ＋ 5 角色子代理**（单会话常驻）

**编队**：主会话＝Orchestrator；子代理＝`vr1-planner`（派发序/计划）· `vr1-designer`（spec/RTL）· `vr1-verifier`（测试/比对/覆盖）·
`vr1-auditor`（独立评审，只读）· `vr1-decider`（一切设计/规格取舍决策，ADR 留痕）。

**循环**：`flow.py next` → 主会话按 plan 的 role 字段派发（结构化派发词）→ 子代理干活并把结论写 `doc/process/out/<step>.json` →
主会话只读该 JSON → 更新 `plan.json/ledger.json` → 下一步。**全程单会话、无第二窗口、无定时任务。**

| 要求 | 满足方式 |
|---|---|
| ①一次跑到里程碑 | 主会话循环至停点（里程碑／需人物理项／同一错误 2 次）；步骤间零请示 |
| ②高效 | 主上下文只装"目标+结论"（C1/C2）；确定性步骤走 runner（C3）；子代理内部重活不污染主窗 |
| ③IC 流程 | 角色对应流程：计划→设计→验证→评审→决策；步骤序＝编译→冒烟→定向→回归→比对→覆盖率→closure |
| ④质量 | 里程碑前 `vr1-auditor` 只读复核（0 阻塞才过）；决策一律 `vr1-decider` 出 ADR；证据＝文件+机判输出 |
| ⑤非定时 | 人一句「跑」触发；或单轮内一口跑到停点 |
| ⑥单对话框 | 子代理在当前会话内派发（不是新 Quest）；不新建对话 |

**依据**：这正是 Anthropic（90.2%）与 Synopsys（50×）公开的 production 形态；"教编排器如何委派"＝结构化派发词+文件化结论。
**风险**：每步一次子代理调用（token 高于纯 runner）→ 用 C3 把可脚本化的步骤压掉。

## 方案 2 **快回路 Runner ＋ Agent 补缺**（最快，v1 方案 A 的升级）

**结构**：`script/flow_run.py` 连续执行确定性步骤；只在**失败或需判断**时叫 `vr1-designer`/`vr1-verifier`/`vr1-decider`；
`vr1-planner` 负责把新步骤脚本化。**优点**：token 最低、最快（ChipAgents 教训：把预算花在把回路做快）；
**缺点**：角色"全程在场感"弱——派发序与决策仍由 agent 做，但大部分动作是脚本。
**适合**：M1 之后的回归/覆盖率/签核阶段（步骤高度确定）。

## 方案 3 **验证先行 Verification-first**（质量最硬，TDD-for-hardware）

**结构**：`vr1-decider`+`vr1-planner` 先定**机器可判的验收判据集** → `vr1-verifier` 先写测试与 golden（ISS/trace/断言/覆盖模型）→
`vr1-designer` 再写 spec/RTL 让测试转绿 → `vr1-auditor` 每里程碑复核 → closure。**依据**：ASIC-Agent 的 cocotb-first（LLM 写 Python 强一个数量级）
＋ VeriBugBench 的"可复查证据"＋ ChipAgents 的"覆盖率幻觉"（用 bug 导向信号，不靠覆盖率数字自嗨）。
**缺点**：RTL 显形慢（先花在判据与测试上）。

## 对比与推荐

| 维度 | 1 编队常驻 | 2 Runner+补缺 | 3 验证先行 |
|---|---|---|---|
| token | 中 | **最低** | 中高 |
| 主窗纯净度 | **最高** | 高 | 高 |
| 一次跑到里程碑 | **强** | 强 | 中（里程碑在"测试全绿"处） |
| 质量面 | **强**（独立评审+ADR） | 中 | **最强** |
| 落地成本 | 中（派发词模板） | 低（脚本） | 中高（先写判据/测试） |

**推荐组合 ＝ 1 为骨架 ＋ 3 为排序原则 ＋ 2 为提速手段**：
主会话常驻编排；验证先行（先判据后实现）；能脚本化的一律 runner 化；里程碑前一次 `vr1-auditor`；
全程单会话、非定时、跑到"里程碑或唯一物理阻塞（装工具链，需管理员+重启）"才停。

## 落地清单（回一句「跑」即执行，≤40 分钟）

1. `plan.json` 每步补 `role` 与 `cmd/evidence`（S2 比对器自检起）。
2. 5 份**结构化派发词模板**（objective／写面／判据／预算／结论落盘路径，≤40 行）。
3. 写 `script/flow_run.py`（确定性步骤直跑；失败→一行摘要给主会话）。
4. 首跑：S2 → S3（需人物理项）自动停，输出报告。
5. 报告回填本节"首次实测"（起止步/耗时/token 估计/停点原因），作为方案 1 的验收证据。

## 首次实测（2026-09-25，方案 1+2+3 首跑 ✓）

- 命令：`python script/flow_run.py`（runner 自动跑 S2 → 停在 S3 需人项）
- 结果：`[PASS] S2 | [trace_compare] 比对 30 条 × 列 ['pc','binary','gpr','csr']，mismatch=0`
- 停点：**S3（H-2 装工具链，需管理员+重启）**——停点规则按设计生效，中途零请示
- 记账：runner 自动写台账（`R-189`）；步骤证据＝`sim/run_S2/run.log`
- 结论：**M1.0 达成**（ISS 冒烟 32/0 ＋ 比对器自检 0 mismatch）；M1 等 S3
- 成本观感：本轮主会话只做「1 条命令 + 1 次回读」，对比旧流程需读 6 份治理文档、手写编号与四件套记录

> 角色对账（方案 1）：S1/S2 归 `vr1-verifier` 职责面（本轮由 runner 确定性执行，无需派遣——C3）；
> S4 的 `cmd` 待 S3 完成后由 `vr1-verifier` 补写；若 S2 失败，则交回 orchestrator 派 `vr1-verifier` 修复（快回路失败路径）。
