## 1. 诊断：旧流程为什么必然长成这样

### 1.1 三句话

1. **判据挂错了对象。** 旧流程把「文档自洽 ＋ 评审新增 0」当作质量判据。文档没有 oracle，
   只能靠"再读一遍找矛盾"这类最弱判据——外部证据：AI 评审意见的采纳率约 19.2%（人类约 60%）、
   模型自我纠错在有外部判据前会**变差**、同模型换角色共享盲点（本项目自己已写死此声明）。
   而 IC 的质量判据原本是可执行的：lint 0 error / trace 0 mismatch / 覆盖率数字 / 形式证明 /
   riscv-test 通过。于是全部力气花在了唯一无法自动判定的东西上。
2. **循环没有承载件。** 旧流程自承"驱动源只有后台任务完成通知与人的消息"；"不得中途停"
   只是 prompt 约束。定时任务三次上线两次被撤（累计存活不足 1 天）；186 条 R 行中 66 条含 R0 介入。
   ⇒ 需求①（一次跑到里程碑）在旧机制里**根本没有承力构件**。
3. **状态住在对话里，编号靠手写。** 每轮开工要读 6 份治理文档；`doc/verify/05` 334 KB、
   评审记录 426 KB、HANDOFF 230 KB，主上下文一开场就吃满。外部证据：compaction 会丢掉
   "当时看不出重要、后来才重要"的约束；有效可用上下文通常只有标称窗口的 25%~50%。

### 1.2 实物对账（流程跑了三天，实物有多少）

| 类别 | 体量 | 说明 |
|---|---|---|
| `rtl/` | **0 行** | 10 个文件全是 `.gitkeep` |
| `sw/` | **0 行** | 2 个 `.gitkeep` |
| `tb/` | 237 行 | UVM 骨架 7 个文件 |
| `iss/` | 5,933 行 | 自研 Python ISS 1,611 行 ＋ 测试/探针（唯一有实质产出的部分） |

| `doc/review/` | **21,781 行 / 138 件** | 含 50 个评审附录、127 个探针件 |

**结论：门槛判据 25 项、评审 5 轮上限、双编号体系、五字段交接——换来 0 行 RTL、0 次 RTL 仿真。**

### 1.3 六个已发生的事实（新方案必须正面处理）

1. **定时任务已证伪**：三次上线两次被撤。需求⑤与它是同一诉求的不同表述。
2. **人是燃料而非评审者**：186 条 R 行里 66 条（35%）含 R0 裁决/指令/签署。
3. **`.qoder/agents/*.md` 在当前运行时不被读取**：ZCode 的配置面只有 `.zcode/` 与 `.agents/`
   （skills/commands/agents/hooks/MCP）；实测本会话可选子代理类型为 `general-purpose`、`Explore`
   与插件提供的 `judge`，**不存在 `vr1-*` 五种角色**。即旧流程的"角色独立性"在运行时层面是文件摆设。
4. **两套 SSOT 并存**：旧（`00`＋`verify/05`＋`AutoQueue.yaml`＋25 项 gate）与新（`ledger.json`＋
   `plan.json`＋`flow.py`）同时活着，R 编号已分叉（R-188 起只在新文件里），两套都在等人批。
5. **判据与产品脱钩**：25 项机判中绝大多数是流程自身的完整性（台账计数、编号连续、看板镜像、
   HANDOFF 字段、RA token 定义），与"RTL 对不对"无关。
6. **人的唯一真阻塞是环境**：ISS-002（WSL2 ＋ RISC-V 工具链，需管理员＋重启）挂了 3 天，
   卡住 M0/M1/M6/M8。而 **RTL 冒烟并不需要它**（见 §3 方案 A 的 M1 定义）。

### 1.4 立即可用的运行时原语（ZCode，实测）

| 原语 | 能力 | 用途 |
|---|---|---|
| `Stop` hook | 可请求**继续**（上限 3 次）；exit 2 阻断结束；stdout JSON 可注入 `additionalContext` | **承载"跑到里程碑"**，替代定时任务 |
| `SessionStart` hook | matcher ∈ `startup` / `resume` / `clear` / **`compact`** | 压缩/续跑后**强制重注入**状态与禁令，对抗上下文丢失 |
| `PreToolUse` hook | 可 `allow` / `ask` / `deny`（exit 2 = deny），可改写参数 | **机械执行写边界**（冻结后 `rtl/` 只读、禁 `rm`） |
| 子代理 frontmatter `tools:` | 按角色给工具白名单；**不给 `Bash`/`Write` 即机械只读** | 让"只读审计"从声明变成事实 |
| 后台任务（`run_in_background`） | 完成时**自动唤醒**会话 | 长跑（仿真/回归）的供能渠道，非定时任务 |
| 工作区技能 `.zcode/skills/` | 按需加载的 SOP | 取代"每轮读 6 份治理文档" |
| 工作区插件 `.zcode-plugin/` ＋ `agents/*.md` | 注册真正的子代理类型；可 `hooks/hooks.json` | 让 5 角色**真正可派发**（修事实 3） |

运维约束（必须知道）：**hooks 在会话启动时被快照，改完 hooks 需重开一次会话**（同一工作区冷启动续跑，
不是"多开对话框"）；配置型 hooks 需 `"enabled": true`；Windows 下优先 `type: "process"` ＋ `args[]`
（免 shell，避开 PowerShell 语法与编码坑）。

## 2. 三方案共享的公理（P1~P8，先立后用）

- **P1 判据只认外部可执行件**：lint/编译、仿真＋golden 比对、形式/等价、覆盖率、回归、错误注入。
  LLM 只做 triage、排序与风险提示，**不做签核**（红线 R8 的机械版）。
- **P2 写操作永远单线程**；只读探索才并行。同一时刻只有一个 writer，其余 agent 只贡献情报。
- **P3 状态只在文件系统**：单一 `state/flow.json` 为唯一真值；编号脚本自增，**禁手写**；
  对话不是存储、不是交接面。
- **P4 每步一个门；同一门连续 3 次不过 ⇒ 停并升级**（3-Strike）；门禁轮次有硬上限与熔断。
- **P5 里程碑 ≤1 人类小时等效**；任何一步坏掉都能**冷启动续跑**（METR：长任务成功率随时长衰减，
  80% 可靠区比 50% 视野短约 4 倍 ⇒ 可靠性由"重启能力"承担，不由"单次会话长度"承担）。
- **P6 LLM 只做三件事**：生成（受写面约束）／决策（ADR 四要素）／triage（附≥1 外部锚点）。
- **P7 上下文预算**：每次注入 ≤2K token（spec 头部 ＋ 当前判据 ＋ ≤30 行失败摘要）。
  确定性步骤的原始日志**不进主上下文**，只落 `evidence/`。
- **P8 循环的三个合法供能渠道**：`Stop` hook 续跑、后台任务完成通知、人的一句话。
  **不使用定时任务**；不使用第二个对话框。

## 3. 三个方案

### 方案 A｜Runner-in-the-Loop（脚本背压 ＋ Hook 强制循环）——**效率优先**

**一句话**：把确定性工作全部下沉到脚本，agent 只在失败点与决策点出现；
用 `Stop` hook 让会话必须跑到里程碑判据为真才允许停。

**编队与写面**

| 角色 | 载体 | 写面 | 出现时机 |
|---|---|---|---|
| 主会话（编排） | 本体 | 只写 `state/flow.json` | 全程 |
| `vr1-designer` | 子代理 | `doc/spec/**`、`rtl/**` | 需要实现/改规格时 |
| `vr1-verifier` | 子代理 | `tb/**`、`sw/**`、`iss/**` | 需要新增判据/激励时 |
| `vr1-auditor` | 子代理，`tools: [Read, Grep, Glob]`（无 Bash/Write） | **无**（机械只读） | 里程碑边界 |
| `vr1-decider` | 子代理 | `doc/decisions/ADR-*.md` | 遇取舍时 |
| `script/flow.py` | 脚本（**零 token**） | `evidence/**` | 每一步 |

**循环怎么转**

1. `python script/flow.py next` → 输出唯一动作（读 `state/flow.json`，脚本决定，不是模型决定）。
2. `python script/flow.py run` → 顺序执行确定性步骤（`vlog` 编译/lint → 仿真 → trace 比对 →
   覆盖率 → 回归）。PASS **只认产物证据行**，不信退出码；FAIL 产出 ≤30 行摘要。
3. 失败或有判断点 → 主会话按 `role` 派一个子代理（结构化派发词 ≤40 行：目标／写面／判据／
   预算／结论落盘路径），子代理**结论写文件**，只回 ≤2K token 摘要。
4. 一轮结束想停 → `Stop` hook 运行 `flow.py gate-stop`：当前里程碑 exit criteria 未达则
   **请求继续**并注入下一条动作；达标则放行（停下等里程碑确认）。

**Hook 配置骨架**（`<repo>/.zcode/config.json`；Windows 用 `process` ＋ `args[]`）

```json
{
  "hooks": {
    "enabled": true,
    "events": {
      "SessionStart": [
        { "matcher": "startup|resume|clear|compact",
          "hooks": [ { "type": "process", "command": "python",
                       "args": ["script/flow.py", "ctx", "--budget", "2000"],
                       "timeoutMs": 20000 } ] }
      ],
      "PreToolUse": [
        { "matcher": "Write|Edit",
          "hooks": [ { "type": "process", "command": "python",
                       "args": ["script/flow.py", "guard-write"], "timeoutMs": 10000 } ] },
        { "matcher": "Bash",
          "hooks": [ { "type": "process", "command": "python",
                       "args": ["script/flow.py", "guard-bash"], "timeoutMs": 10000 } ] }
      ],
      "Stop": [
        { "hooks": [ { "type": "process", "command": "python",
                       "args": ["script/flow.py", "gate-stop"], "timeoutMs": 60000 } ] }
      ]
    }
  }
}
```

判据语义：exit `0` 放行，exit `2` 阻断（`PreToolUse` 即 deny，`Stop` 即请求继续）；stdout 只输出
一个 JSON 对象（严格 schema，多一个键即校验失败）。`guard-write` 在接口冻结后拒绝对 `rtl/**`
的写入；`guard-bash` 拒绝 `rm`、拒绝对受保护路径的重定向与覆盖。

**里程碑定义（关键：不依赖尚缺的工具链）**

| 里程碑 | 判据（全机器可判） | 依赖 |
|---|---|---|
| **M1（今天就能跑）** | `vlog` 编译 **0 error** ＋ 定向激励下 **RTL-vs-ISS 逐指令 trace 0 mismatch** ＋ lint error 0 | 无（ModelSim 本机已有；激励由 Python 生成 `.hex`，**一份镜像喂两边**：TB `$readmemh` 与 ISS 读同一文件） |
| M2 | riscv-tests `rv64ui` 定向子集全过 ＋ arch-test 接入 | **需 WSL2（ISS-002，人执行）** |
| M3 | 覆盖率达 `AGENTS.md` §4 阈值 ＋ 回归 0 UVM_ERROR ＋ 错误注入保真度抽检通过 | M2 |

> M1 的判据刻意绕开 RISC-V GCC：立刻可跑，且直接证明"双线闭环"成立。
> 这正是把 `doc/process/00` ISS-010 的"一份镜像喂两边"纪律工程化。

**质量怎么保证**：判据 100% 外部工具；审计子代理**机械只读**（无 Bash）；反自欺靠
**错误注入/mutation 抽检**（随机打坏 RTL 一处，看 checker 是否报错）——比"再读一遍文档"强一个数量级。
**效率账**：确定性步骤 0 token；主上下文只装"目标＋判据＋失败摘要"；子代理探索不污染主窗。
**弱点**：RTL 设计与难 debug 仍是 agent 的活；难步骤上会"卡住 → 升级"，不会自愈。

### 方案 B｜Spec-as-Checker（可执行规格 ＋ 验证先行）——**质量优先**

**一句话**：把"评审收敛"这个不可满足的任务换成"checker 收敛"：
每条需求在写下时就带可执行判据，于是"规格是否自洽"从"读一遍"变成"跑一遍"。

**需求行 = 可执行七元组**（照抄 TU Wien verification plan 行结构 ＋ EARS 句式）

| 列 | 内容 | 例 |
|---|---|---|
| ID | 需求号 | `R-EXU-004` |
| 需求（EARS） | `WHEN <条件> THE SYSTEM SHALL <行为>` | WHEN 收到未对齐访存 THEN SHALL 触发 misalign 异常 |
| 意图 | 自然语言时序性质 | 异常优先级高于写回 |
| 判据 A（形式） | SVA named property | `p_misalign_exc`：误对齐请求后 1~3 拍内必现 exc（property 体落在 spec 对应篇） |
| 判据 B（仿真） | 覆盖点 ＋ 定向激励 ＋ 期望 | `coverpoint misalign_type` ；激励 `t_mis_0007` |
| 方法 | formal / sim / both | both |
| 通过判据 | **可执行命令** | `make fpv MODULE=exu` → 0 unresolved；`run t_mis_0007` → 0 mismatch |

**写不出第 4／7 列的条目 = 规格未完成，不许进 RTL。**

**编队与循环**：与方案 A 同（同一个 `flow.py` ＋ hook 层），差别只在**判据来源**与**里程碑定义**：
milestone = "VPLAN 第 k 组需求的 checker 全绿"。verifier 先写 golden（ISS 断言 ＋ 定向激励 ＋
覆盖模型 ＋ 比对脚本），designer 再让它们转绿（tests-fail-first）。

**收敛判据（与旧流程的根本差别）**

- 旧：`新增 0`（文档概念，已被自己的记录证明不可满足：阻塞计数 21→10→17→15 非单调）。
- 新：`未通过的 checker 数`——天然单调可减，且**没有解释空间**。
- 反自欺三层：① 判据锚点必须绑官方件/riscv-spec 提取件/Spike；② 错误注入保真度；③ 形式在环
  （外部证据：约 44.2% 通过 testbench 的 RTL 在形式验证下失败；约 80% 的功能错误对编译器不可见）。

**效率账**：前期多花在判据与 golden 上，但每个后续步骤都变成"跑脚本"而非"读文档＋写评语"。
**弱点**：接口几何/位宽这类纯选择型需求，可执行化收益低（走 ADR 即可）；RTL 显形慢。

### 方案 C｜Squad Sprint ＋ 对抗性质检（编队冲刺）——**独立性优先**

**一句话**：5 角色编队、写边界由 `tools:` 白名单与 hook **机械锁定**；
每个里程碑交付一个"证据包"，由独立质检队用对抗手段决定是否放行。

**编队**：planner（派发序，脚本化后基本消失）／designer／verifier／auditor（只读）／decider。
**写操作单线程**，只读探索并行（外部证据：Cognition"share full traces"＋"writes stay single-threaded"；
Anthropic 明确"大多数编码任务不适合多代理"）。

**角色必须真正可派发**：把 5 份定义从 `.qoder/agents/` 迁到工作区插件
`tools/vr1-plugin/.zcode-plugin/plugin.json` ＋ `agents/*.md`（frontmatter `name`/`description`/`tools`），
否则它们永远只是文件摆设（§1.3 事实 3）。

**里程碑交付包**（每个 milestone 一个目录）
`RTL ＋ TB ＋ evidence/（log 尾行＋关键数字＋命令＋种子）＋ 覆盖报告 ＋ bug 台账 ＋ 未决项`。

**质检怎么对抗**：auditor **只看 spec ＋ diff ＋ 工具输出**，不看实现者推理（干净上下文；
外部证据：干净的 verifier 平均每个 PR 找 2 个 bug、约 58% 属严重级）。加三类对抗手段：
① 变异/错误注入；② 盲测（只给接口，不给实现的激励）；③ 反向推演（从实现反推它假设了什么规格）。

**人的介入 = 批量批准包**（知识库明确许可的机制）：里程碑边界把"需要人批的"（基线/冻结/放宽/签核
＋ 高风险 ADR）打成一包，人回一句编号，agent 批量执行。**不再逐项请示**，也不再每轮呈报。

**效率账**：token 高于 A（编队开销）；适合"质量与独立性优先"的阶段（G1 后 RTL 实现与签核）。
**弱点**：容易退化成表演性分工——必须配知识库的判据：「新角色必须堵一个**已发生**的失效，否则不得增设」。

## 4. 六条要求 × 三方案对账

| 要求 | A Runner-in-the-Loop | B Spec-as-Checker | C Squad Sprint |
|---|---|---|---|
| ①一次跑到里程碑 | **强**：`Stop` hook 强制续跑 ＋ 脚本决定下一步 | **强**：同 A；里程碑判据更硬 | **中**：编队协调开销大，停点更多 |
| ②高效 | **最强**：确定性步骤 0 token，注入 ≤2K | 中：前期付判据成本，后期极省 | 中低：多角色 token 开销 |
| ③IC 流程 | **完整**：编译→仿真→比对→形式→覆盖→回归→签核 | **最完整**：需求→性质→SVA→覆盖点→验证方法→通过判据 双向可追溯 | 完整：角色对应流程职责 |

| ⑤非定时 | 是（hook ＋ 后台任务） | 是 | 是 |
| ⑥单对话框 | 是（同一会话内派子代理） | 是 | 是（子代理非新会话） |

## 5. 对比与推荐

| 维度 | A | B | C |
|---|---|---|---|
| 落地成本 | **低**（1 个脚本 ＋ 3 个 hook） | 中高（判据与 golden 先行） | 中（角色迁移 ＋ 派发词） |
| 首次可跑时间 | **今天**（M1 不需 GCC/WSL2） | 数天 | 数天 |
| token 成本 | **最低** | 中 | 中高 |
| 质量上限 | 高 | **最高** | 高 |
| 独立性 | 中（审计只读） | 中 | **最高** |

**推荐（单一主线，非并列三选一）：A 为骨架 ＋ B 的局部判据内核 ＋ C 的对抗质检作里程碑门。**

理由：三者回答的是三个**不同**问题，不重叠也不可互相替代——
A 回答"循环谁来驱动"（当前最大缺口，且旧机制无承力构件）；
B 回答"判据从哪来"（旧流程的病根，但必须**按模块增量**兑现）；
C 回答"独立性从哪来"（只在里程碑边界兑现，日常循环为它付费不划算）。

**为什么不是单选**
- **单选 B 有陷阱**：把 14 篇规格一次性全量可执行化 ＝ 又一次"先造文档、后跑代码"，
  极可能重演"三天 0 行 RTL"。B 只能**按当前正在实现的模块**增量落地（M1 先做它需要的那一小撮需求）。
- **单选 C 与外部证据冲突**：协调税高，且"多数编码任务不适合多代理""写操作必须单线程"是
  已有多方实证；C 的价值集中在里程碑边界，不适合当日常骨架。
- **单选 A 不保证对**：A 只管循环承载与"没被改坏"，不提供"判据来源"与"没验到"的独立性。

**分档落地顺序**
1. **第 0 档（今明两天，先让循环转起来）**：A 全部（`flow.py` ＋ 3 个 hook ＋ `state/flow.json`）
   ＋ **M1 那一小组需求的 B 形态判据**。目标是跑出第一个真实的 RTL-vs-ISS trace 0 mismatch。
2. **第 1 档（M1 之后、G1 之前）**：B 按模块铺开（需求可执行七元组），C 暂不启用。
3. **第 2 档（G1 后 RTL 实现期与签核）**：C 在里程碑边界启用（对抗性质检 ＋ 批量批准包），
   日常循环仍是 A。

**任何一档都不新增"流程判据"**：新流程的门只判产品（编译/比对/覆盖/形式/回归），
流程自身的完整性由脚本副产品承担，人零成本。

## 9. 诚实的边界（做不到 / 不确定）

1. **"一次会话跑到天荒地老"做不到。** 可靠性来自"里程碑 ≤1 人类小时 ＋ 冷启动可续跑 ＋ 3-Strike"，
   不是来自单次会话长度。任何承诺"一键跑到流片"的方案都不成立。
2. **"任何决策都由 agent"有硬边界。** 知识库 RA1 规定关键节点人签，且不可回退事项必须等人明确选择。
   本方案能做的是把人的介入从"每轮"压到"里程碑边界的一次批量确认"。
3. **hook 续跑有上限（3 次）**，跨过即需要一次"新会话冷启动续跑"——这不是"多开对话框"，
   而是把长任务切成可重启单元；状态在 `state/flow.json`，冷启动无损。
4. **M1 之后立刻撞上环境阻塞**（WSL2/GCC，ISS-002），那一步只能人做。方案已把不需要它的部分前置。
5. **规格可执行化（方案 B）对"纯偏好型"取舍无效**，那类只能走 ADR；不应对它承诺机器判据。

> **环境口径更正（2026-09-25，R-235/R-236）**：上述第 4 条与 §2 对比表"首次可跑时间"栏所依据的
> 前提「环境阻塞＝WSL2/GCC，只能人做」**已不成立**——R0 定「**永不装 Linux**」后改 **MSYS2 纯 Windows
> 路线**，AI 已自行装齐（`riscv64-unknown-elf-gcc` 16.1.0／Verilator 5.050／**Spike 自建**／QEMU，
> **免管理员、免重启**），证据 `sim/run_env_msys2/run.log`，步骤与坑见 `doc/环境搭建.md`。
