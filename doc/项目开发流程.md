## 2. 验证策略五问（动手前必须回答，逐项定死）

### 2.1 层次【策略】【管理】

设计自顶向下划分、验证自底向上集成。**能在低层次验证的功能不上高层**；高层优先复用低层的
参考模型/监视器/比较器。

| 层次 | 对象 | 该层独占的价值 | 环境 | 分配的功能点 |
|---|---|---|---|---|
| L1 单元级 | 20 个模块各一（`spec/00` §6 M01~M20） | 可控性最强、仿真最快、**适合断言 + 形式验证** | 小 TB + Python 对拍模型 | 表结构/算法/状态机/边界与非法输入 |
| L2 核对级 | `vr1_core` | 乱序引擎交互：依赖距离、冲刷时机、资源争用 | UVM 平台 + golden ISS trace 比对 | RAW/WAW、投机恢复、forwarding、ROB/LQ/SQ 满 |
| L3 系统级 | hart + CLINT/PLIC + AXI 存储（SoC-lite） | 中断/NMI/trap 时序、非缓存访存、总线合规 | UVM 平台 + AXI 从端 VIP | 中断源×时机×嵌套、PMA/IO、`fence.i` |
| L4 程序级 | 真实程序（riscv-tests / arch-test / 裸机 RTOS） | 长时间稳态、指令组合、**唯一能证明"能跑软件"** | `riscv-dv`/`pygen` 产程序 → ISS 与 RTL 双跑 | 指令组合、hazard 密度、soak |

**L1↔L4 的强制要求**：任何在 L4 发现的失败，必须先按【管理】"到更小环境、用更少变量复现"
下沉到 L1/L2 复现并定位，修复后先跑小环境出错场景，再跑 L2/L4 两级回归。

### 2.2 透明度【策略】

**灰盒为主**，且明确"哪一层黑、哪一层白"：

| 手段 | 用在哪 | 不用在哪 |
|---|---|---|
| 断言（SVA） | 内部不变式：RAT/PRF free-list、ROB 头序、CAM 单命中、队列空满、AXI 握手规则、PMP 判决 | 不做功能收敛的唯一判据 |
| 参考模型（自研 `iss/`） | L2/L4 的输入输出裁决：**逐指令退休比对** | 不建模微架构时序（那由断言与覆盖率负责） |
| 监测器（monitor） | 接口边界（AXI/中断/trace）+ 少量**状态类**内部信号 | 不测中间变量类信号（时序不稳定，有害收敛） |
| force / backdoor | 仅限调试定位 | **禁止用于任何正式判定**（红线 R8 + 规则 17：正式判定必须前门 + 显式检查） |

灰盒开关纪律【策略】：新增检查点/断言**每次只开少量并跑回归**，便于把失败快速归因到新开的开关。
本项目对应"白盒开关分优先级"——`tb/vr1_uvm` 的检查器使能位必须可按名开关并写文档。

### 2.3 激励【计划】【策略】

CPU 核 DV 的本质特征：**激励以"程序"为单位，不是总线事务**【ibex】。

| 层 | 激励源 | 自由度控制 |
|---|---|---|
| L1 | 单元 TB 的约束随机事务（Python 生成器 / SV constrained random） | 六类因素：静态约束 / 反馈偏置 / 功能开关 / 结构成员 / 环境配置 / 组件同步【计划】 |
| L2~L4 | `riscv-dv`（主用 `pygen` 纯 Python 路线，规避"生成器要仿真器"）+ 自研 `iss/vriss/encode.py` 出定向程序 | 定向流按 hazard/loop/load-store 组合注入 |
| 全程 | 非合法输入（错误响应、超时、随机中断、非法指令注入） | 错误激励是一等公民：`+illegal_instr_ratio`、总线错误响应、中断同拍 |

**约束域三阶段节奏**【策略】（本项目量化进 `doc/03`）：

```
基本功能阶段（L2 初通）    窄约束 → 先覆盖基本功能，不碰边界
完备功能阶段              逐步放开到全部合法组合
功能覆盖 ≥ 80% 后         收窄 + 偏置（biasing），定向打剩余空洞
                        （宽约束此时产出的种子对覆盖率几乎无贡献）
```

### 2.4 检查手段分工【策略】【计划】

| 被检查对象 | 首选手段 | 本项目具体件 |
|---|---|---|
| 单元内部逻辑/状态机 | 断言 + 形式验证 + 参考模型对拍 | L1 TB + Python 模块模型（预测器/RAT/队列/PTW 各一个） |
| 核输入输出（指令语义） | 参考模型 + 比较器 | `iss/vriss` + `iss/tools/trace_compare.py` |
| 数据通路转换 | 参考模型 + 线上比较 | 退休 trace 逐指令比对（默认比 `pc,binary,gpr,csr`） |
| 总线/协议合规 | 协议监测器 + 断言（VIP 优先） | `tb` 的 AXI protocol checker（对照《AMBA-AXI协议导读》） |
| 集成连接/访问路径 | 断言 + 定向测试 | L3 SoC-lite 连线路径遍历 |
| 属性穷举 | 形式验证（RVFI 喂 riscv-formal） | **待决策 ISS-017**：采纳 RVFI 兼容退休接口后白捡 |

**"激励器只管接口协议、不模拟相邻设计内部功能"**【管理】——本项目的 mem agent（I/D 总线从端）
只做：随机响应时延 + 随机错误响应 + 保序合同，不建模缓存行为。

### 2.5 环境与工具【计划】

双轨固定分工（已写入 `AGENTS.md` §3 与 README）：ModelSim SE = UVM/覆盖率/签核；
WSL Verilator = 跑量与性能；**性能指标禁止在 ModelSim 上测**。
静态检查不可省略【计划】：本项目单时钟域 → CDC 检查降级为"若日后加异步 FIFO 才启用"，
但 **lint 与语义检查（不可达逻辑/死状态/X 传播）必须在每次 RTL 提交前跑**（`verilator --lint-only`，
见 `spec/11`）。

### 3.1 场景分解 12 维 → VR1 各块的选用【场景】

| 被测块 | 场景分解维度（§4.x） | 为什么选它 |

| LSU M11 | 4.7 交互序列 + 4.5 三分 | Load/Store 三流程各是一条序列；非对齐/页内跨界是边界 |
| MMU/PTW M12 | 4.6 配置空间 | 页大小 × 权限位 × ASID × PMP 模式 的矩阵（组合爆炸 → Pairwise 瘦身） |
| Cache/总线 M13/M14 | 4.8 状态×事件 + 4.9 FMEA | valid/dirty/MSHR 状态机 × 事件；缺失回填失败是故障模式 |

| 中断/CLINT/PLIC M19 | **4.10 事件/中断驱动分解** | 源 × 触发时机 × 嵌套 × 屏蔽窗内触发 |

### 3.2 验证点方法 34 种 → VR1 的推荐组合【场景】§5.35

| 被测特征 | 知识库推荐组合 | VR1 具体用途 |
|---|---|---|
| CSR 位域 | 等价类 + 边界值（含健壮性/最坏情况扩展） | 每个 WARL 位：写合法/非法/全 1/全 0，读回核对 |
| 多条件逻辑 | 因果图 → 判定表 | 中断三条件 (a)(b)(c) 与委托 → 2³ 判定表 + 优先序表 |
| 多因素配置 | 正交表 / **Pairwise** / 分类树 CTM | PTW：{4K,2M,1G} × {R,W,X,U,G} × {ASID 命中/失配} × {PMP 模式} |
| 状态机 | 状态转换测试 + FSM 覆盖（高要求上 W-method） | Cache 行状态、LSU 休眠-唤醒、PTW FSM |
| 数据通路 | **参考模型比对** + 数据通路激励法 + 属性驱动 | 退休 trace 比对（本项目主线） |
| 协议接口 | 语法测试 + 协议一致性测试 | AXI4 合规 ~70% 起点（《标准协议验证经验》口径） |
| 覆盖率收敛 | 控制流 + 基路径 + 数据流（MC/DC 按需） | 代码覆盖 ≥90% 的补用例手段（对应 `doc/07`） |
| 用例集质量 | **变异测试** | 自检"我的检查器够不够狠"——本项目已被 `trace_compare` 注入单点错误实证过一次 |
| 容错/恢复 | 故障注入 + 场景法备选流 | 总线错误响应、NMI、double fault |
| 优先级排序 | FMEA 驱动 | 决定 P1/P2 验证点分级（对齐设计风险） |
| 需求条目 | 需求导向测试（追溯矩阵） | `doc/01` 功能点 ↔ `doc/02` 验证点 ↔ 用例 三向映射 |
| 经验沉淀 | 基于检查表 + 错误推测 | `spec/11` RTL 评审 checklist；本台账 ISS-011~016 全部是"这类问题会二刷"的素材 |
| 新 IP 摸底 | 探索式测试 | 首次跑通 riscv-dv 随机流时 |
| 轻量快探 | 随机 + 错误推测 + 探索式 | L2 早期冒烟 |

**每条验证点必须指定检查手段**（"跑了没报错"不算检查）——红线 R8 的分解层落地。

## 4. 度量与收敛（五指标 + VR1 特有两条）

| # | 指标【计划】§十二 | 本项目口径 | 阈值（见 `AGENTS.md` §4） |
|---|---|---|---|
| 1 | 回归测试通过率 | 回归表分**基本功能表**与**带优先级高级表**两档；随机用例必须记录种子 | 全绿 0 UVM_ERROR；≥2 轮同配置 0 新 FAIL |
| 2 | 代码覆盖率 | 语句/条件/决策(FSM/分支) 六类，`vcover merge` 批级合并后判 | **先冲 ≥90% 语句+决策**再分析其余【计划】 |
| 3 | 断言覆盖率 | 动态断言覆盖 + （若采纳 RVFI）静态属性覆盖合并 | 报告项，逐条有归属验证点 |
| 4 | 功能覆盖率 | 三面向采样：输入组合 / 输出时序 / **内部状态与验证点一一对应** | 100%（doc/02 口径） |
| 5 | 缺陷曲线 | 按周记录提交/修复/关闭；盯斜率收敛 | 见 §5 |
| **+6** | **ISS 一致性率**（本项目特有） | `与 ISS 逐指令 0 mismatch 的程序数 / 总程序数`，按 seed 记录 | 签核前 100%（含异常类白名单程序） |
| **+7** | **配置成熟度**（借 ibex） | 每个参数配置标 **Red / Amber / Green**，只有 Green 进签核 | 见 §6.3 |

**缺陷曲线的两个管理动作**【周期】【计划】：

1. 斜率不收敛 → 停下补场景，不许靠加机器硬堆；
2. **覆盖率已收敛却还在暴露基本功能缺陷 = 亮红灯**，必须回看验证计划与环境本身
   （本项目对应动作：重过 Review G1/G2 的自检清单，不是补几个用例了事）。

## 5. 回归门禁与节奏【管理】

| 时机 | 门禁 | 本项目落地 |
|---|---|---|
| RTL 提交前 | 设计者自检基本功能，**通过才允许 check-in** | `script/regress.py --gate`：lint + 单元回归 + 该模块 trace 对拍；不过不合入 |
| 每模块单元就绪 | 建立"基本功能回归表"，必须先全绿 | 该模块 unit TB + 与 Python 模型对拍 ≥1000 随机事务（M4） |
| 核级集成后 | 反复提交回归 + 大规模随机检验稳定性 | L2/L4 双轨；每轮收覆盖率并反馈偏置 |
| 缺陷修复后 | **同种子复现 → 修复 → 同种子复验 → 两级回归** | `doc/05` 记种子，`doc/06` 记六字段 |
| 项目后期 | 不换仿真器/脚本版本（避免引入新变量） | 工具版本写进 `doc/10` 基线记录 |
| 长用例提效 | 切分场景 / 状态快进 / 两阶段法 / 给足并行 | 对应 `spec/13` 的性能测试与 soak 用例设计 |

> "切分 + 状态快进"对 CPU 尤其有效：跑真实程序时把"初始化到目标状态"的那一段用
> 两阶段法跳过（先验证跳转条件成立，之后所有用例直接强置初始状态寄存器）——
> 但强置属白盒手段，**只能用于缩短激励时间，判定仍必须前门 + 显式检查**。

## 7. 调试规程（Step 6 的操作手册）

### 7.1 Agans 九法则 → IC 落地【调试】

理解系统 / 让它失败（稳定复现）/ 停止猜测去看 / 分而治之 / 一次只改一个变量 /
保持审计记录 / 检查插头（复位、宏、路径、license、编译选项顺序）/ 获得新鲜视角（= 红线 R2
"停止-报告"的制度化）/ 没修好就是没修好。

### 7.2 六步标准过程【调试】

```
① 稳定复现（固定 seed、收窄激励）→ ② 收集事实（波形/log/版本与配置差异）
→ ③ 假设-实验循环（二分 + 单变量对照 + KT 的 IS/IS-NOT 差异）
→ ④ 根因确认（三备齐：能解释全部现象、能主动重现、修复后消失）
→ ⑤ 修复+验证（同种子复验 → 两级回归；doc/06 全程记录）
→ ⑥ 预防再发（补断言/checker/checklist——最常被跳过，跳过则同类必二刷）
```

### 7.3 使用分级（不把 RCA 用成流程税）【调试】

| 层 | 触发 | 用什么 | 成本 |
|---|---|---|---|
| 日常 ~90% | 任何问题默认起点 | 九法则 + 科学循环，脑内完成不填表 | 分钟级 |
| 疑难 ~10% | 卡住 > 2 h / 越修越糟 / 修了又犯 | 加显式假设-实验记录（`doc/06` 逐轮）+ KT IS/IS-NOT | 小时级 |
| 正式 罕见 | 同类二刷 / 涉多人交接 / 逃逸下游 / 项目要求 | 七段骨架 + 8D 增补段，进 `doc/00` + 缺陷单 | 天级 |

`debug/` 下所有定位/移交/取证文档一律用 **§4A 七段骨架**（现象 / 排除链 / 证据链 /
RTL 与模型代码对照 / 根因假设 / 结论与移交 / 复现与证据索引），已在 `AGENTS.md` 规则 19 引用。

### 7.4 本项目特有的"四方归因优先序"

漫游指南的顺序是"先查环境 → 序列 → 参考模型 → 设计"【周期】。VR1 的参考模型是**自研的**，
它自己就是未签核的代码，所以归因链必须多一层、且顺序不能反：

```
比对失败
 ① 查比对器/tb（列口径、归一化、位宽、seed 是否同源）      ← 最便宜，且完全可控
 ② 查自研 ISS（它有没有实现该指令的 corner？规范怎么说？）  ← 本项目 80% 的假 DUT bug 在这层
 ③ 查 RTL（下沉 L1/L2 小环境复现）
 ④ 查 spec（谁与 RISC-V 规范不符？规范是最终仲裁者）
```

配套硬规则：**禁止**为了让 RTL 变绿而改 ISS 行为（红线 R6）；第 ② 步认定 ISS 错时，
必须先在 `doc/00` 立"验证代码"条目、注明规范条款出处，再改，再同种子复验。
本轮实测已验证这条链有效：冒烟 4 个 bug（ISS-013~016）全部在第 ①②步被抓出，没有一个是被"改判为 DUT bug"混过去的。

## 9. 评审与自检（谁来批、批什么）

### 9.1 三个 Review 与 TR 的对应

| Review | 对应 TR | 材料 | 人的动作 | AI 的提交前自检 |
|---|---|---|---|---|
| **Review G1**（= Requirement Review，含接口冻结） | TR2 + TR3 + PDCP | `spec/00~14`、`doc/01`、`doc/03` | 逐篇评审签署；三处高风险优先（`spec/04` 端口数、`spec/07` forwarding、`spec/10` CSR） | 规格原文通读无遗漏 / 每条功能点标出处 / 存疑单列不臆测 / 接口-寄存器-时钟复位三张假设表齐 |
| Verification Point Review | — | `doc/02` | 评审（最关键，漏一条 = 漏一类 bug） | 覆盖 `doc/01` 100% / 每条有方法+激励+检查手段 / 边界异常并发专项 / 无"待补充" |
| **Review G3** = Sign-off | TR6 | `doc/07/08/09` + `doc/00` | 签核 | 功能覆盖 100% / 代码覆盖达标且 waiver 逐条批 / 回归全绿 / 台账闭环 / 缺陷有处置结论 |

### 9.2 检查点 1 的特殊处理（本项目最大流程风险）

【周期】的检查点 1 要求"**系统、设计、验证三方**回顾验证计划"，目的是暴露三方对功能文档的
理解分歧。本项目 spec 由 AI 自产、验证者也是 AI —— **作者 = 被评审人**，三方退化成一方的风险真实存在
（已登记 `doc/00` ISS-008）。

补偿措施（写死进流程，不可省略）：

1. **人必须逐篇签署 Review G1**，不接受 AI 自评通过；
2. 三处"高风险易错"内容强制人读：端口数推导（`spec/04`）、forwarding 单拍可实现性（`spec/07`）、
   CSR WARL 位段（`spec/10`）——这三处错了，下游"错得看起来很对"；
3. 每个数值结论必须带**规范 §号或书页码**出处，人可回查；无出处即视为臆测，退回；
4. 用**自证伪**替代第三方评审：任何"通过"结论必须给出一个"若逻辑错则会报红"的反证实验
   （本轮 `trace_compare` 注入单点错误即为一例），并记入 `doc/05`；
5. **角色拆分与对抗评审子代理**：R1（规格）/R2（参考模型，禁读 `rtl/`）/R3（RTL）/R4（平台）
   /R6（审计）/R7（信息隔离的对抗评审）职责与读写边界见
   **`doc/AI角色与职责.md`**——它把"三方"重建成互不可写的产物 + 一个看不到作者推理的独立读者。
   同一文件 §1.2 明写了残余风险：**同模型多角色共享盲点，该机制只削弱不消除**。

### 9.3 基线机制【九步】

基线时机 = **Review G1 签署** 或 **平台 smoke 通过**，二者取先。基线动作：固化版本（git tag 或目录快照号）
→ 建 `doc/10-基线记录.md`（基线号/日期/范围/平台版本/当时 doc 状态/工具版本）→ 更新 `AGENTS.md` 基线状态。
基线后：`rtl/` 转只读（红线 R1 口径见 `AGENTS.md` §5.1），平台改动先报告待批（R5）。
