## 2. 验证策略五问（动手前必须回答，逐项定死）

### 2.1 层次【策略】【管理】

设计自顶向下划分、验证自底向上集成。**能在低层次验证的功能不上高层**；高层优先复用低层的
参考模型/监视器/比较器。

| 层次 | 对象 | 该层独占的价值 | 环境 | 分配的功能点 |
|---|---|---|---|---|
| L1 单元级 | 20 个模块各一（`spec/00` §6 M01~M20） | 可控性最强、仿真最快、**适合断言 + 形式验证** | 小 TB + Python 对拍模型 | 表结构/算法/状态机/边界与非法输入 |
| L2 核对级 | `vr1_core` | 乱序引擎交互：依赖距离、冲刷时机、资源争用 | UVM 平台 + golden ISS trace 比对 | RAW/WAW、投机恢复、forwarding、ROB/LQ/SQ 满 |
| L3 系统级 | hart + CLINT/PLIC + AXI 存储（SoC-lite） | 中断/NMI/trap 时序、非缓存访存、总线合规 | UVM 平台 + AXI 从端 VIP | 中断源×时机×嵌套、PMA/IO、`fence.i` |
| L4 程序级 | 真实程序（riscv-tests / arch-test / 裸机 RTOS） | 长时间稳态、指令组合、**唯一能证明"能跑软件"** | `riscv-dv`/`pygen` 产程序 → ISS 与 RTL 双跑 | 指令组合、hazard 密度、soak |

**L1↔L4 的强制要求**：任何在 L4 发现的失败，必须先按【管理】"到更小环境、用更少变量复现"
下沉到 L1/L2 复现并定位，修复后先跑小环境出错场景，再跑 L2/L4 两级回归。

### 2.2 透明度【策略】

**灰盒为主**，且明确"哪一层黑、哪一层白"：

| 手段 | 用在哪 | 不用在哪 |
|---|---|---|
| 断言（SVA） | 内部不变式：RAT/PRF free-list、ROB 头序、CAM 单命中、队列空满、AXI 握手规则、PMP 判决 | 不做功能收敛的唯一判据 |
| 参考模型（自研 `iss/`） | L2/L4 的输入输出裁决：**逐指令退休比对** | 不建模微架构时序（那由断言与覆盖率负责） |
| 监测器（monitor） | 接口边界（AXI/中断/trace）+ 少量**状态类**内部信号 | 不测中间变量类信号（时序不稳定，有害收敛） |
| force / backdoor | 仅限调试定位 | **禁止用于任何正式判定**（红线 R8 + 规则 17：正式判定必须前门 + 显式检查） |

灰盒开关纪律【策略】：新增检查点/断言**每次只开少量并跑回归**，便于把失败快速归因到新开的开关。
本项目对应"白盒开关分优先级"——`tb/vr1_uvm` 的检查器使能位必须可按名开关并写文档。

### 2.3 激励【计划】【策略】

CPU 核 DV 的本质特征：**激励以"程序"为单位，不是总线事务**【ibex】。

| 层 | 激励源 | 自由度控制 |
|---|---|---|
| L1 | 单元 TB 的约束随机事务（Python 生成器 / SV constrained random） | 六类因素：静态约束 / 反馈偏置 / 功能开关 / 结构成员 / 环境配置 / 组件同步【计划】 |
| L2~L4 | `riscv-dv`（主用 `pygen` 纯 Python 路线，规避"生成器要仿真器"）+ 自研 `iss/vriss/encode.py` 出定向程序 | 定向流按 hazard/loop/load-store 组合注入 |
| 全程 | 非合法输入（错误响应、超时、随机中断、非法指令注入） | 错误激励是一等公民：`+illegal_instr_ratio`、总线错误响应、中断同拍 |

**约束域三阶段节奏**【策略】（本项目量化进 `doc/03`）：

```
基本功能阶段（L2 初通）    窄约束 → 先覆盖基本功能，不碰边界
完备功能阶段              逐步放开到全部合法组合
功能覆盖 ≥ 80% 后         收窄 + 偏置（biasing），定向打剩余空洞
                        （宽约束此时产出的种子对覆盖率几乎无贡献）
```

### 2.4 检查手段分工【策略】【计划】

| 被检查对象 | 首选手段 | 本项目具体件 |
|---|---|---|
| 单元内部逻辑/状态机 | 断言 + 形式验证 + 参考模型对拍 | L1 TB + Python 模块模型（预测器/RAT/队列/PTW 各一个） |
| 核输入输出（指令语义） | 参考模型 + 比较器 | `iss/vriss` + `iss/tools/trace_compare.py` |
| 数据通路转换 | 参考模型 + 线上比较 | 退休 trace 逐指令比对（默认比 `pc,binary,gpr,csr`） |
| 总线/协议合规 | 协议监测器 + 断言（VIP 优先） | `tb` 的 AXI protocol checker（对照《AMBA-AXI协议导读》） |
| 集成连接/访问路径 | 断言 + 定向测试 | L3 SoC-lite 连线路径遍历 |
| 属性穷举 | 形式验证（RVFI 喂 riscv-formal） | **待决策 ISS-017**：采纳 RVFI 兼容退休接口后白捡 |

**"激励器只管接口协议、不模拟相邻设计内部功能"**【管理】——本项目的 mem agent（I/D 总线从端）
只做：随机响应时延 + 随机错误响应 + 保序合同，不建模缓存行为。

### 2.5 环境与工具【计划】

双轨固定分工（已写入 `AGENTS.md` §3 与 README）：ModelSim SE = UVM/覆盖率/签核；
WSL Verilator = 跑量与性能；**性能指标禁止在 ModelSim 上测**。
静态检查不可省略【计划】：本项目单时钟域 → CDC 检查降级为"若日后加异步 FIFO 才启用"，
但 **lint 与语义检查（不可达逻辑/死状态/X 传播）必须在每次 RTL 提交前跑**（`verilator --lint-only`，
见 `spec/11`）。

### 3.1 场景分解 12 维 → VR1 各块的选用【场景】

| 被测块 | 场景分解维度（§4.x） | 为什么选它 |

### 3.2 验证点方法 34 种 → VR1 的推荐组合【场景】§5.35

| 被测特征 | 知识库推荐组合 | VR1 具体用途 |
|---|---|---|
| CSR 位域 | 等价类 + 边界值（含健壮性/最坏情况扩展） | 每个 WARL 位：写合法/非法/全 1/全 0，读回核对 |
| 多条件逻辑 | 因果图 → 判定表 | 中断三条件 (a)(b)(c) 与委托 → 2³ 判定表 + 优先序表 |
| 多因素配置 | 正交表 / **Pairwise** / 分类树 CTM | PTW：{4K,2M,1G} × {R,W,X,U,G} × {ASID 命中/失配} × {PMP 模式} |
| 状态机 | 状态转换测试 + FSM 覆盖（高要求上 W-method） | Cache 行状态、LSU 休眠-唤醒、PTW FSM |
| 数据通路 | **参考模型比对** + 数据通路激励法 + 属性驱动 | 退休 trace 比对（本项目主线） |
| 协议接口 | 语法测试 + 协议一致性测试 | AXI4 合规 ~70% 起点（《标准协议验证经验》口径） |
| 覆盖率收敛 | 控制流 + 基路径 + 数据流（MC/DC 按需） | 代码覆盖 ≥90% 的补用例手段（对应 `doc/07`） |
| 用例集质量 | **变异测试** | 自检"我的检查器够不够狠"——本项目已被 `trace_compare` 注入单点错误实证过一次 |
| 容错/恢复 | 故障注入 + 场景法备选流 | 总线错误响应、NMI、double fault |
| 优先级排序 | FMEA 驱动 | 决定 P1/P2 验证点分级（对齐设计风险） |
| 需求条目 | 需求导向测试（追溯矩阵） | `doc/01` 功能点 ↔ `doc/02` 验证点 ↔ 用例 三向映射 |

| 轻量快探 | 随机 + 错误推测 + 探索式 | L2 早期冒烟 |

## 4. 度量与收敛（五指标 + VR1 特有两条）

| # | 指标【计划】§十二 | 本项目口径 | 阈值（见 `AGENTS.md` §4） |
|---|---|---|---|
| 1 | 回归测试通过率 | 回归表分**基本功能表**与**带优先级高级表**两档；随机用例必须记录种子 | 全绿 0 UVM_ERROR；≥2 轮同配置 0 新 FAIL |
| 2 | 代码覆盖率 | 语句/条件/决策(FSM/分支) 六类，`vcover merge` 批级合并后判 | **先冲 ≥90% 语句+决策**再分析其余【计划】 |
| 3 | 断言覆盖率 | 动态断言覆盖 + （若采纳 RVFI）静态属性覆盖合并 | 报告项，逐条有归属验证点 |
| 4 | 功能覆盖率 | 三面向采样：输入组合 / 输出时序 / **内部状态与验证点一一对应** | 100%（doc/02 口径） |

| **+6** | **ISS 一致性率**（本项目特有） | `与 ISS 逐指令 0 mismatch 的程序数 / 总程序数`，按 seed 记录 | 签核前 100%（含异常类白名单程序） |
| **+7** | **配置成熟度**（借 ibex） | 每个参数配置标 **Red / Amber / Green**，只有 Green 进签核 | 见 §6.3 |

**缺陷曲线的两个管理动作**【周期】【计划】：

1. 斜率不收敛 → 停下补场景，不许靠加机器硬堆；
2. **覆盖率已收敛却还在暴露基本功能缺陷 = 亮红灯**，必须回看验证计划与环境本身
   （本项目对应动作：重过 Review G1/G2 的自检清单，不是补几个用例了事）。

## 7. 调试规程（Step 6 的操作手册）

### 7.1 Agans 九法则 → IC 落地【调试】

理解系统 / 让它失败（稳定复现）/ 停止猜测去看 / 分而治之 / 一次只改一个变量 /
保持审计记录 / 检查插头（复位、宏、路径、license、编译选项顺序）/ 获得新鲜视角（= 红线 R2
"停止-报告"的制度化）/ 没修好就是没修好。

### 7.2 六步标准过程【调试】

```
① 稳定复现（固定 seed、收窄激励）→ ② 收集事实（波形/log/版本与配置差异）
→ ③ 假设-实验循环（二分 + 单变量对照 + KT 的 IS/IS-NOT 差异）
→ ④ 根因确认（三备齐：能解释全部现象、能主动重现、修复后消失）
→ ⑤ 修复+验证（同种子复验 → 两级回归；doc/06 全程记录）
→ ⑥ 预防再发（补断言/checker/checklist——最常被跳过，跳过则同类必二刷）
```

### 7.3 使用分级（不把 RCA 用成流程税）【调试】

| 层 | 触发 | 用什么 | 成本 |
|---|---|---|---|
| 日常 ~90% | 任何问题默认起点 | 九法则 + 科学循环，脑内完成不填表 | 分钟级 |
| 疑难 ~10% | 卡住 > 2 h / 越修越糟 / 修了又犯 | 加显式假设-实验记录（`doc/06` 逐轮）+ KT IS/IS-NOT | 小时级 |
| 正式 罕见 | 同类二刷 / 涉多人交接 / 逃逸下游 / 项目要求 | 七段骨架 + 8D 增补段，进 `doc/00` + 缺陷单 | 天级 |

`debug/` 下所有定位/移交/取证文档一律用 **§4A 七段骨架**（现象 / 排除链 / 证据链 /
RTL 与模型代码对照 / 根因假设 / 结论与移交 / 复现与证据索引），已在 `AGENTS.md` 规则 19 引用。

### 7.4 本项目特有的"四方归因优先序"

漫游指南的顺序是"先查环境 → 序列 → 参考模型 → 设计"【周期】。VR1 的参考模型是**自研的**，
它自己就是未签核的代码，所以归因链必须多一层、且顺序不能反：

```
比对失败
 ① 查比对器/tb（列口径、归一化、位宽、seed 是否同源）      ← 最便宜，且完全可控
 ② 查自研 ISS（它有没有实现该指令的 corner？规范怎么说？）  ← 本项目 80% 的假 DUT bug 在这层
 ③ 查 RTL（下沉 L1/L2 小环境复现）
 ④ 查 spec（谁与 RISC-V 规范不符？规范是最终仲裁者）
```

配套硬规则：**禁止**为了让 RTL 变绿而改 ISS 行为（红线 R6）；第 ② 步认定 ISS 错时，
必须先在 `doc/00` 立"验证代码"条目、注明规范条款出处，再改，再同种子复验。
本轮实测已验证这条链有效：冒烟 4 个 bug（ISS-013~016）全部在第 ①②步被抓出，没有一个是被"改判为 DUT bug"混过去的。

## 9. 评审与自检（谁来批、批什么）

### 9.1 三个 Review 与 TR 的对应

| Review | 对应 TR | 材料 | 人的动作 | AI 的提交前自检 |
|---|---|---|---|---|
| **Review G1**（= Requirement Review，含接口冻结） | TR2 + TR3 + PDCP | `spec/00~14`、`doc/01`、`doc/03` | 逐篇评审签署；三处高风险优先（`spec/04` 端口数、`spec/07` forwarding、`spec/10` CSR） | 规格原文通读无遗漏 / 每条功能点标出处 / 存疑单列不臆测 / 接口-寄存器-时钟复位三张假设表齐 |
| Verification Point Review | — | `doc/02` | 评审（最关键，漏一条 = 漏一类 bug） | 覆盖 `doc/01` 100% / 每条有方法+激励+检查手段 / 边界异常并发专项 / 无"待补充" |
| **Review G3** = Sign-off | TR6 | `doc/07/08/09` + `doc/00` | 签核 | 功能覆盖 100% / 代码覆盖达标且 waiver 逐条批 / 回归全绿 / 台账闭环 / 缺陷有处置结论 |

### 9.2 检查点 1 的特殊处理（本项目最大流程风险）

【周期】的检查点 1 要求"**系统、设计、验证三方**回顾验证计划"，目的是暴露三方对功能文档的
理解分歧。本项目 spec 由 AI 自产、验证者也是 AI —— **作者 = 被评审人**，三方退化成一方的风险真实存在
（已登记 `doc/00` ISS-008）。

补偿措施（写死进流程，不可省略）：

1. **人必须逐篇签署 Review G1**，不接受 AI 自评通过；
2. 三处"高风险易错"内容强制人读：端口数推导（`spec/04`）、forwarding 单拍可实现性（`spec/07`）、
   CSR WARL 位段（`spec/10`）——这三处错了，下游"错得看起来很对"；
3. 每个数值结论必须带**规范 §号或书页码**出处，人可回查；无出处即视为臆测，退回；
4. 用**自证伪**替代第三方评审：任何"通过"结论必须给出一个"若逻辑错则会报红"的反证实验
   （本轮 `trace_compare` 注入单点错误即为一例），并记入 `doc/05`；
5. **角色拆分与对抗评审子代理**：R1（规格）/R2（参考模型，禁读 `rtl/`）/R3（RTL）/R4（平台）
   /R6（审计）/R7（信息隔离的对抗评审）职责与读写边界见
   **`doc/AI角色与职责.md`**——它把"三方"重建成互不可写的产物 + 一个看不到作者推理的独立读者。
   同一文件 §1.2 明写了残余风险：**同模型多角色共享盲点，该机制只削弱不消除**。

### 9.3 基线机制【九步】

基线时机 = **Review G1 签署** 或 **平台 smoke 通过**，二者取先。基线动作：固化版本（git tag 或目录快照号）
→ 建 `doc/10-基线记录.md`（基线号/日期/范围/平台版本/当时 doc 状态/工具版本）→ 更新 `AGENTS.md` 基线状态。
基线后：`rtl/` 转只读（红线 R1 口径见 `AGENTS.md` §5.1），平台改动先报告待批（R5）。

### 9.4 评审收敛两档制（增量复核轮 + 终局全量复核轮）【R0 2026-09-23 定】

设立依据：`spec/01` 连跑 8 轮不收敛。实测阻塞项计数 21 → 10 → 17 → 15，**不单调**；而旧问题闭环率
87%→100%→65% 在升——病灶在"新增"侧。逐条追溯可证：新增项多数是**上一轮修复在接口链上又接了一段、
远端还没定义**（缺冲刷键、无生产者的信号、CSR 通路没有来源）。在此前提下仍按【收敛】§6.1 C2 要求
"新增 0"，等于要求一篇还有 12 篇未与之合流的规格一次性全篇自洽，**不可满足**，于是循环无出口。

**两档定义**

| 档 | 复核面 | 收敛判据 | 何时跑 |
|---|---|---|---|
| **增量复核轮** | **改动集** ＝ **机算**（`changed` 的改动节 ∪ 被改标识符的引用闭包）**＋ 作者补报**的节；作者只能**加**不能减——机算集之外的节若被作者声明改过，须说明为何 diff 里没有（见下方"为什么必须有'引用闭包'这一半"） | ① 上轮旧问题逐条真改（按落点原文核对，不采信"已改"字样）② 改动集及其闭包内新增 0 | 每次处置轮之后，可连跑多轮，直到新增 0 |
| **终局全量复核轮** | **整篇** | 【收敛】§6.1 C2 对全篇成立：新增 0 且旧问题全改 | 仅当增量轮判"无问题"之后 |

顺序固定为：**全量 → 处置 → 增量（可若干轮）→ 全量 → …**

为什么必须有"引用闭包"这一半：本项目最大的一类缺陷**住在没改的那一侧**。实例——附 E 的 N9（`rt_t`
要 `pc/rd_data/mem_*/csr_*`，而承载方 `commit_t` 那节本轮未动、全文 0 处含这些名字）、N10、X1
（`spec/00` §7.3 一行未改却与本篇新定案相反），以及缺失型 N1（"§5.2 `CT` 行没写弹栈动作"——
不存在的行不出现在 diff 里）。只审作者声明的段落会同时漏掉这四类，故改动集由机器生成、不由作者自报
（作者自报已有前科：第 7 轮抓到"自报待办四项中三项半未落地"）。工具：`python script/gate.py changed`。

**基线纪律：每轮处置开工前先提交一次 git 基线**（R0 2026-09-23 定）

纳管方式取 ISS-001 的 ②：沿用本机 **Git for Windows**（实测 `git version 2.52.0.windows.1`，`.gitattributes` 已在）。
⚠ 执行口径（ISS-001 二次更正注，2026-09-23）：`git` **未入系统 PATH**，裸调 `git` 会失败——每条 git 命令前加
`set "PATH=%PATH%;C:\Users\HHHXXX\AppData\Local\GitHubDesktop\app-3.6.4\resources\app\git\cmd"`，
或由人把该目录加入 PATH 后删去此前缀。
处置轮开工的**第一件事**：`git commit` 一次受控产物，提交信息写 `<队列号> r<n> 基线`；此后
`python script/gate.py changed <该 commit>` 才等于"**本轮**改动"，而非自上上次粗提交以来的累计差异。
**不提交就开工 = 改动集失真 = 复核面无从界定**，这条与红线 R3（可追溯）同源，不得省略。

**远端同步纪律：先 `pull` 查冲突 → 再 `commit` → 再 `push`**（R0 2026-09-23 定，登记 `doc/05` R-021）

远端＝`https://github.com/HHHXXX-cell/virtual_riscv.git`（私有仓，`origin/main`）。每轮的动作顺序固定为：

| 序 | 动作 | 要点 |
|---|---|---|
| ① | **`git pull --rebase origin main`（或先 `fetch` 再比对）** | **提交前先同步**：确认有无远端新提交、有无冲突。**有冲突先解冲突再往下**（解冲突按"保留双方语义"原则，必要时呈人；不得用 `-X ours/theirs` 盲解、不得 `reset --hard` 丢远端或本地工作） |
| ② | `git commit` | 按上方基线纪律：处置轮开工先提交 `<队列号> r<n> 基线`，处置后按路径显式提交 |
| ③ | **`git push origin main`** | 每轮收尾必须把本地提交推到 `origin`——**只 commit 不 push ＝ 远端与本地脱钩**，换机/协作时改动集失据（本次实测：本地曾积累 16 个未推送提交才发现） |

⚠ **环境前提（2026-09-23 实测）**：①直连 `github.com:443` 不通，须走本机代理——单次 `-c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897`（**不写入 git 配置**）；②私有仓需凭据，本机凭据管理器暂无 `github.com` 条目 ⇒ **首次须由人认证一次**（见 `doc/05` R-021 的选项），之后命令行即可免交互 pull/push。


时序注意：基线提交发生在**处置轮开工前**，不是复核轮开工前——若在处置改完之后才提交，
待复核的 diff 会被自身提交吃掉。首轮例外已记录：`spec/01` v0.3 处置当时未提交，
其基线即现有 `HEAD`（`a8a63f5`），本轮增量复核以该 commit 为基线。

**派发分片规则（2026-09-23 加：R0 建议 + 实测）**

复核轮与决策轮的**派发一律分片，且按"修改点／决策项"切**：

| 对象 | 分片规则 | 每片必读 |
|---|---|---|
| **增量复核轮** | **一个修改点一片**（`changed` 改动节里的每个节＝一片）；跨节的核销类项（台账计数／看板镜像／记录对账／闭包未展开分流）归**一个公共片** | 该节的现文 ＋ **该片所属被改标识符的闭包命中处**（取自 `changed` 输出，即"必读清单"） |
| **决策 AI（ADR）** | **一个决策项一片**（一项一份 ADR） | 该决策涉及的一至两节 ＋ 其锚点出处（规范/参考核，按"Grep 定位后读命中处"） |

依据（`doc/05` R-021 实测）：整批派发时两件任务各耗 ~9-12M token、19-20 min 后被模型服务拒绝、**无产出**——
单片上下文可控，且**单片失败不拖累整轮**（失败片可原地重派，其余片照常出结论）。
派发词须给每片写明**硬性预算**（目标时长、工具调用上限）与**"查不完即列盲区"**的允许，禁止整篇通读大文件。

**复核面 ＝ 七来源并集（缺一不可；⑦ 为不可枚举类，只能由全量轮承担）**

| 来源 | 取法 | 为什么不能省 |
|---|---|---|
| ① 本轮改动集 | `python script/gate.py changed <基线commit>`：改动节 + 被改标识符的引用闭包 | 覆盖"改了 A 没改 B"的断链（N5/N9/N10/X1 型） |
| ② 上一轮复核记录的未闭环项 | `doc/spec/<篇>-评审记录.md` 各附录中判"未改 / 部分 / 待澄清"的条目 | 改动集看不到"上一轮答应了却没动"的账（第 7 轮实测四项中三项半未落地） |
| ③ 跨篇待闭合清单 | 出口第 2 条所登记 | 未写篇目持有的类型/参数，本篇 diff 里永远不出现 |
| ④ 机判输出的未决项 | `changed` 的"闭包未展开"逐项、`width_check` 的未能核实 / TITLE-MISMATCH、`check` 的 WARN | 机器只指出"可疑"、不判"是否缺陷"；无人认领就等于让工具发现的问题无人判读 |
| ⑤ 上轮**自报**的诚实边界 | 评审者自报"未核验 / 超取证范围"（附 G 自报未读 `doc/00`）；作者自报"未做"（附 F 的 F-5 清单） | 属**流程欠账**而非产物缺陷；不列为来源就会静默蒸发 |
| ⑥ 转派 / 路由项 | 评审记录中判"转 `<他篇>` / 归 `<他角色>`"的条目（S1/SUS-01 → `spec/04`、ISS-037 → R2） | 复核要确认它们仍在追踪，而非被"已转出"当闭环 |
| ⑦ **缺失型**（该写没写） | **无取法**——不存在的行不出现在 diff 里（N1："§5.2 `CT` 行没写弹栈动作"） | 结构上只能由**终局全量复核轮**的语义推演承担；这是"全量轮不可省"的唯一硬根据 |

**④ 需分流后再定级**：`changed` 的"闭包未展开"项里混着 ③ 类的复述（模块名 / 未写篇目持有的端口，如
`vr1_exu_int`、`ptw_fill_valid`）、改名留痕（`ckpt_held_vec`、`exc_t`）与真断链，复核者按"生产者/消费者是否存在"
逐条分流，**不得一律记缺陷、也不得一律放过**（工具尾注同此声明）。

**所以增量复核轮 ≠ 只审 diff**：②③⑤⑥ 来自**历史核查记录**、④ 来自当轮机判，它们的性质都是
"改动集之外仍必须付的账"。
复核报告引用位置一律"文件 + 节号"（节号稳定可 grep），可另附 `<commit>:<节号>` 固定版本。

**上限与出口（硬）**

1. **全量轮上限 5 次**。`full_rounds` 记的是**已消耗**的全量轮数（不是"下一轮编号"）：一旦达到 5 且仍未收敛，
   即置 `fused` 并 `escalate` 转 R0，**不得默认通过、不得自行加轮**（红线 RA1 与 RA3；字段在
   `run_cmd/AutoQueue.yaml`，由 `gate.py` 的 `queue-full-round-cap` 机判）。**人可越权**——但须在队列项里写
   `cap_waiver`（谁在何时批的），机判随之改打 `queue-full-round-cap-waiver` 并原文回显批文；无批文的越权一律 FAIL。
   实例：Q-004 已消耗 5 轮（第 3/5/6/7/8 轮全篇纯复核），现持 R0 2026-09-23「继续直到收敛」批文继续。
2. **跨篇未闭合项不计入本篇新增**：应由尚未撰写的篇目持有的类型与参数（如 `spec/00` §6 引用而 `spec/01`
   未定义的 15 个类型、`ipend_t`、`bp_upd_id` 表深），登记进"跨篇待闭合清单"，从本篇阻塞数中剔除；
   但**Review G1 冻结前该清单必须清零**——放宽的是本篇的收敛判据，不是冻结判据。
3. **取证格式**：评审产物内引用位置一律"文件 + 节号"，禁止行号（行号随编辑漂移，每轮为重新定位交税）。
   同一约定 `run_cmd/AutoQueue.yaml` 头部本已写明，此前未覆盖到评审记录。
4. 终局全量轮的报告须给出**档位声明 + 取证范围自报**（读过哪些节、未审哪些），并继续受"禁止宣布通过/冻结"约束。

**与角色边界的关系**：本条只切分评审者的**算术义务**（机判已覆盖者抽查当哨兵、未覆盖者一律实算，见
`doc/AI角色与职责.md` 与 `.qoder/agents/vr1-auditor.md`），**未**给只读评审角色增加执行工具——
机判输出由领队生成后随派发词喂入。依据：全量人工复算 28 个 struct 的那一轮贡献 **0** 个发现，
而该轮 12 个阻塞全部来自语义/时序推演；提速只能买回机械的一半。

- **spec 内的设计空间取舍（机制语义、接口几何、位宽/参数取值、时序约定）＝日常技术决策，AI 自决**（2026-09-23 R0 口径：spec 是**设计 AI 的承诺**，非人的承诺；R1 为领域第一负责人）：方法＝**先 L1 本地知识库路由精读、不足再 L2 网络检索**，然后**列 2~3 种方案并评估**（依据链、代价、风险、回退方式）**择优**。**决策记录（ADR）四要素必须齐**：①选项与评估 ②选定 ③**外部锚点**（规范 §号 / Spike / 参考核 / 算式 / 可证伪实验——无锚点者不得记"已定"，降级为"登记＋预测＋回退点"）④**下游义务清单**（此选择为真时哪几篇、哪些接口要跟着改——"提前预判"的落点）。**成本分级**：a) 被规范或 `spec/00` §4 唯一确定 → 只记"由 X 决定"；b) 有 2~3 个可行解 → 完整 ADR；c) 纯偏好 → 登记＋回退点。**不可回退项**（接口/位宽/协议语义）允许 AI 定，但**禁止走"超时默认"路径**，且必须进 §9.5 评审 list 的 ④ 段供人读。同一问题 3 次未决即熔断出决策包转人（`vr1-decider.md`）；

- 例行技术选型（在已有方案框架内），例：脚本用 Python driver 还是 ps1。

- **自动推进循环（2026-09-23 R0 定，不停自转）**：**① 决策 AI 决策**（设计/规格类取舍 → ADR，§12.2 授权；§12.5 可被审核一次、非决定性）→ **② 计划 AI 出/更新计划**（`vr1-planner`：下一批工作项＋依赖序＋出口判据，落盘为 `run_cmd/AutoQueue.yaml` 项与 `doc/04` 状态）→ **③ 执行角色落地**（R1~R5，按队列 `role` 切角色）→ **④ 完成后再由计划 AI 给下一版计划**（按 §9.4 复核结果与台账闭环情况滚动）。**人只在 P1~P4（§12.1）与 §12.3 三类必报项介入**；循环每圈仍须留痕（`doc/05` + HANDOFF + 机判），**不得以"自动"为由跳过复核或默认通过**。
  **执行断点纪律（2026-09-23 实测补，R0 追问"为什么没有自动继续"）**：循环的驱动力只有两个——**后台任务完成通知**与**人的消息**；**若某轮收尾时没有任何后台片在跑，循环即断**。故：**每轮收尾前必须至少派出一片下一批工作**（派发词＋预算齐备），否则视为"停摆"；确需停摆（等人裁定/等环境）时必须显式写明"停因 + 恢复条件"并记 `doc/05`。

  - **载体**：`doc/03-验证计划.md` **§0 驱动计划**（有序工作项表：`序｜工作项｜角色｜产物落点｜出口判据｜派发词要点｜依赖/阻塞`）。**计划 AI 是唯一作者**；R8 只执行（转队列项、派发、核销、回填状态列），**不得自行改序或跳项**。
  - **周期协议**：①每轮开工跑 `gate.py check`（0 FAIL）→ ②执行《驱动计划》**队首项**（按其"派发词要点"分片派发）→ ③该项核销（出口判据达成＋机判通过）→ ④**调计划 AI 一次**（`vr1-planner`）**重排驱动计划**（据 §9.4 复核结果、台账闭环、队列就绪面）→ ⑤回到 ②。

  - **不得以"自动"为由免检**：每圈照旧机判＋留痕（`doc/05`＋HANDOFF）；评审门禁（§9.4/§9.5）与红线（R6/R7/R9/R10）不受本机制影响。

### 12.3 但下列三类属“必须上报”，不得自决（哪怕会打扰人）

### 12.5 决策审核（一次·只记录；2026-09-23 R0 定，登记 `doc/00` ISS-042 追加项）

**适用对象**：决策 AI（`vr1-decider`）按 §12.2 下的**每项设计决策**（ADR）。

| 项 | 规定 |
|---|---|
| **谁审** | 审核 AI（角色 R6/R7，`vr1-auditor`）；全程只读，不得改产物 |
| **几次** | **一次**——同一决策首次给出后可执行一次独立审核；决策被修订（重开 ADR）时可再审一次，不重复审同一版本 |
| **审什么（以风险为主轴；R0 2026-09-23 追加口径）** | 只问一件事：**这个决策有什么风险、有多大、有没有兜底**。按五类风险源逐条列并标严重度：①**判错风险**——锚点是否存在且可回查（无锚点 ⇒ 错判无从察觉）②**不可逆风险**——回退方式是否可行、代价多大 ③**下游风险**——下游义务缺失（"该写没写" ⇒ 断链由别人承担）④**自洽风险**——决策与新写正文自相矛盾（⇒ 实现分叉、误译）⑤**致死风险**——会致死的时序/接口反例（须给触发条件）。每条须写 **触发条件 + 影响面 + 现有兜底**（锚点/断言/覆盖/进 list 人读），并给**残余风险结论**：`可接受` / `需进 §9.5 list ④段人读` / `需决策 AI 回应`。**非风险类发现**（措辞、体例、编号）**不入决策审核清单**——转记录类按原流程处置 |
| **记在哪** | `doc/05`（每决策一行：审核人/时间/发现数/发现摘要）+ 审核报告追加进 `doc/spec/01-评审记录.md` 对应附件；**不得删除或淡化**（红线 RA4） |
| **效力（关键）** | **审核结果不作决定性反驳依据**：不自动回退决策、不阻断其生效、不使该决策"未定"；**由决策 AI 在"剩余分歧"中回应**（可修正、可维持原判并说明理由）。审核发现同时进 §9.5 评审 list 的 ③段（风险与残余）与 ④段（不可回退项），**供人签署时读** |
| **例外（不变）** | ① **R6/R7 类**（放宽比对/waiver/改检查器/删 bins）**不是**"决策 AI 的决策"，恒第 0 次转人；② 人对 G1/G3 的签署权、P3 的批准权不变；③ 若审核发现属"决策**无锚点**"，该项在 ADR 记录中**只能标"登记＋预测＋回退点"**（§12.2 原有要求，不因审核而放宽）；④ 审核发现若指向**记录/一致性缺陷**（如引用对账、计数口径）仍按原流程处置——本条只免除"对技术决策的决定性反驳"，不豁免记录与一致性义务 |
