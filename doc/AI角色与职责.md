## 1. 独立性从哪来（先定原理，再定角色）

### 1.1 四种"独立性"按真实价值排序

| 序 | 来源 | 是否真机制 | 说明 |
|---|---|---|---|
| ① | **外部不可篡改的裁判** | ★★★ 最强 | RISC-V 规范原文（本地 `_tools\riscv-spec.pdf` / `riscv_spec_full.txt`）、**Spike**、覆盖率数据库数字、**注入错误实验**。任何结论都必须绑定其中至少一个 |
| ② | **信息隔离的独立读者** | ★★★ 真机制 | 子代理拿不到作者的推理链,只拿到"被评审产物 + 规范条款"→ 等价于【调试】法则 8"获得新鲜视角"的制度化 |
| ③ | **产物读写边界** | ★★ 防串改 | 角色只能写自己那格目录,跨角色只读;交接以文件为输入(【九步】关键机制) |
| ④ | 提示词里"你现在是验证工程师" | ☆ **无价值** | 同模型换 prompt 不产生新盲点。**禁止把它当独立性的证据写进任何报告** |

### 1.2 一条必须写死的残余风险声明

> **同一模型扮演的多个角色共享盲点。** 作者犯的推理错误,评审角色有相当概率一并复现。
> 因此多 AI 角色只能**削弱**、不能**消除**自证风险。残余部分由两件事兜底：
> ① 每个关键结论必须绑一个 ①类外部锚点（规范条款 / Spike 比对 / 注入实验 / 覆盖率原始报告）；
> ② 三级 Review 结论权只在人（R0）。**任何"AI 自己评审通过"都不构成门禁放行条件。**

## 4. 落地的四个机制（有工具支撑，不是设想）

### 4.1 信息隔离评审（R7）—— 本文件里唯一"技术上新增"的能力

**做法**：每篇 spec / 每块 RTL 提交评审时，派**独立子代理**，输入**只有**：

```
① 被评审产物的路径（不给作者推理、不给对话历史、不给上一轮结论）
② 指定锚点：如"RISC-V 特权规范 §3.1.6 mstatus 位段"、【超】p.187-188
③ 任务模板：
   "你是独立评审者，不是作者。逐条列出：
    (a) 你无法从文本判定对错的地方（缺定义/缺位宽/缺条件）
    (b) 与给定锚点条款相冲突的地方（引条款号）
    (c) 你认为会导致死锁/假绿/漏测的具体场景（给触发条件）
    (d) 你确认无误的部分不要写
    禁止给结论性'通过'判定。"
```

**为什么有效**：子代理的上下文是新的,不会被作者的自洽叙事带偏。这是"作者=评审人"风险的
唯一结构性解法,其余都是补偿性检查。

**输出归置**：质疑清单进被评审文档篇首"评审记录"节,作者必须**逐条回应**（改文 / 说明为何不改 + 锚点）,
R6 核对是否逐条闭环。**禁止静默改写**【调试】§4A 纪律②。

### 4.2 代码评审（`CodeReview` 子代理）

对 `iss/`、`tb/`、`rtl/`（G1 前）的改动派 CodeReview,重点三问：逻辑错、假绿风险（检查器被无意放宽）、
可追溯性缺口。审代码**不等于**授权改 RTL（红线 R1 不变）。

### 4.3 角色固化

用 `create-subagent` 把 R6（审计）、R7（对抗评审）做成仓库内的子代理定义文件,使角色不依赖
某个会话的记忆。定义里写死 §2 的禁写清单与 §4.1 的任务模板。

### 4.4 外部锚点登记（每个关键结论可反查）

| 锚点类型 | 具体件 | 用于兜哪类风险 |
|---|---|---|
| 规范原文 | `_tools\riscv-spec.pdf`、`_tools\extracted\riscv_spec\riscv_spec_full.txt`（可 grep） | R1/R2 的理解偏差 |
| 第三方 ISS | Spike（装好后，ISS-002） | R2 自研模型的正确性——**唯一能独立裁决 R2 的东西** |
| 参考实现 | `_tools\picorv32-main`、`ibex-master`、`cv32e40p-master` | 接口/验证环境惯例是否被自创 |
| 可证伪实验 | `iss/tests/test_smoke.py` + `trace_compare.py` 注入单点错误 | "检查器是否真的能报红"（已做一次，见 `doc/00` ISS-013~016） |
| 工具自报数 | `vcover report` 原始输出、回归 log | 覆盖率与通过判定的数字造假（红线 R7/R8） |

**硬规则**：任何写进 `doc/02` 验证点、`doc/07` 覆盖率结论、`doc/09` 一致性结论的判据,
必须指向以上至少一个锚点;只有"我认为/我推导"的一律标 `待锚点`,R6 不予勾销。

## 6. 成本纪律（防止角色膨胀）

1. **角色数封顶 9 个**（R0~R8；2026-09-23 由 8 升 9）。加一个角色必须先说明它堵的是哪个**已发生**的失效,
   否则不加——子代理调用有真实的时间与算力成本,违反红线 R9 的资源约束精神。
   **R8 的举证已立**（`doc/00` ISS-033）：① 无"开工即自动捡任务"的执行体；② B1~B8 阻塞项无人催办；
   ③ ISS-021/022/031 三次"声明与实态脱钩"缺逐轮核销触发者；④ 14 条待决策无催办。
   并按 §6.3 检验通过：R8 新增队列、看板镜像、调度留痕**三处产物边界**，非表演性角色。
2. **R7 只在四个时机调用**：每篇 spec 定稿前、`spec/04/07/10` 三处高风险必调、
   RTL 模块 unit 通过后、Sign-off 前。**不做每轮调用**（边际收益低）。
3. **不为"像团队"而分工**：④ 类表演性分工一律禁止。判断标准——去掉这个角色后,
   如果没有任何产物边界或锚点发生变化,那它就是表演。
4. **冲突处理**：两角色结论冲突时不"投票",一律升级到 R0,并把冲突点记入 `doc/00`
   （分类按流程文档 §6.1 映射表）。

| ④ | **形成闭环而非一次性** | 轮 2a 的 8 类致命项已修，回归由新建的 `iss/tests/test_isa_semantics.py` 23 项断言钉住（官方指令字写死），`KNOWN_OPEN` 13 类随运行打印 —— 评审→处置→落实证据→防再发齐全 |

### 8.3 新发现的一项执行障碍（必须记取）

**“只读”约束靠 prompt 承诺无效**：轮 2 执行后核查发现，两名评审者在仓库 `script/tmp/` 新建了
**34 个探针与输出文件**（尽管提示词写了“不得修改仓库文件”）。核对结论：

| 核查项 | 方法 | 结果 |
|---|---|---|
| 是否改动了既有文件 | 比对全部 tracked 文件的 mtime 与评审时间窗口 | **未发生**（窗口内无任何既有文件被写） |
| 是否新建了未授权文件 | 与登记清单比对 | **发生 34 个** → 约束被违反（仅位置无害，落在临时区） |
| 后果 | `script/tmp/` 被 `.gitignore` 排除 ⇒ **证据会被丢** | 已处理：29 个迁至 `iss/tests/probes/`、5 个迁至 `doc/spec/01-评审探针/`，升格为 ISS-019/020 的证据索引 |

**制度修正（已入 AGENTS 规则 22 与 ISS-022）**：角色写禁令必须有**机械验收动作**，不靠声明：
每轮评审后由 R6 跑一次“仓库清单 + mtime 比对”，输出进 `doc/05`；评审探针不得留在忽略区，
必须归入受版本控制的证据目录。

### 8.4 可执行性的边界（不得越读结论）

1. **它不能替代人**：R7 无法判定“Q17 映射历史栈方案够不够深”这类设计决策，那仍是 `spec/04` 推导 + P1 评审点的内容。
2. **同模型共享盲点未被排除**：两个评审者与我同源；他们没发现的问题，我不能声称不存在。
   真正的外部裁判仍是：**规范原文 / Spike / 官方 `encoding.h` / 覆盖率原始报告 / 可证伪实验**。
3. **评审者也会错**（轮 2b 的“ROB 不可达”过头、把 2.9 Mb 算成 3.4 Mb 的估算差异）：
   因此“会掩盖 bug X 项”不能直接转成台账事实，**必须作者复算后才能定处置**——复算结果也要写进台账。
4. 结论：**多 AI 角色的可执行性成立**，但它的作用是把“人的评审带宽”从逐行审代码提升到
   只读四张结果表（§12.1 的 P1~P4）；**门禁主体仍是人，不因子代理报得很满而改变。**
